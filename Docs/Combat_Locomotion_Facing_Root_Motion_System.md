# Metaworld — Combat Locomotion, Facing & Root Motion System

**Status:** Canonical / Approved Modern RPG Playlist Upgrade

**Engine:** Unreal Engine 5.8

**Runtime Direction:** Blueprint-first / animation-layered / movement-resolver integrated / server-authoritative

## Canonical Principle

Combat locomotion presents the posture required by the active handling profile while the Character Movement/Action systems remain authoritative for speed, rotation permission and movement legality. Attack rotation and root motion can improve commitment and responsiveness, but they cannot override collision, target validity, encumbrance or action restrictions.

> Combat animation reads the current weapon/action state and shapes movement around it. It does not become a second movement controller.

# 1. Combat Locomotion Profile

Handling/equipment can select a combat locomotion profile such as:

- Unarmed;
- One-Handed;
- Two-Handed;
- Shield;
- Dual Wield;
- Bow;
- Handgun;
- Rifle;
- Heavy/Improvised;
- Magic-ready.

The profile may choose:

- idle pose set;
- walk/run/sprint locomotion source;
- upper-body overlay;
- turn behavior;
- stride/stance;
- aim/guard layer;
- IK/grip profile;
- movement-speed presentation range.

Use profile/tag/data selection rather than one global CombatType enum.

---

# 2. Motion Matching / Blend Space Compatibility

A custom 1D Blend Space is approved as a prototype/content path for weapon-specific movement.

Metaworld may use:

- Motion Matching/Pose Search for high-fidelity combat locomotion where coverage exists;
- Blend Spaces for focused weapon profiles;
- Linked Animation Layers for combat overlays;
- lower-cost simpler profiles for distant NPCs.

No single technique is mandated for every combat state.

---

# 3. Movement Speed Comes From Resolver

Animation reads effective movement speed/velocity generated by the canonical movement resolver.

Do not set:

`Combat Blend Space Max = 600`

and treat that number as gameplay truth.

If Encumbrance, injury, potion use, water, status or another system changes effective movement, combat animation receives the resulting speed/profile.

---

# 4. Weapon Collision / Body Overlap

Weapon-specific locomotion is approved to prevent unacceptable self-clipping.

Solutions can include:

- authored combat idle/walk/run poses;
- socket/attachment adjustment;
- IK grip correction;
- Control Rig cleanup;
- body-aware animation variants;
- equipment-specific stance.

Do not shrink the player's approved body customization range solely to accommodate one weapon pose.

---

# 5. Attack Facing / Rotation Window

Attacks may define an authored facing-adjustment phase.

Possible flow:

`Attack starts`
-> resolve desired facing target from control/lock-on/target context
-> validate maximum allowed turn and movement state
-> during authored RotationWindow, interpolate/warp character toward approved facing
-> lock/reduce further rotation when the attack profile requires commitment.

A maximum turn such as 90 degrees is a tutorial tuning example, not universal canon.

Each attack profile can define:

- no correction;
- limited correction;
- full face-target correction;
- turn-speed/curve;
- lock-on behavior;
- cancel/interrupt policy.

---

# 6. Camera Direction Is Intent, Not Authority

Using control rotation/camera direction as an attack-facing input is approved.

But camera yaw alone does not automatically permit:

- rotating through blocked movement constraints;
- hitting targets behind walls;
- snapping 180 degrees during a committed heavy attack;
- bypassing stun/knockdown/traversal restrictions.

The combat action/profile validates how much facing adjustment is legal.

---

# 7. Root Motion Forward Movement

Authored forward movement in melee attacks is approved.

Examples:

- short sword step;
- committed lunge;
- shield bash step;
- heavy overhead advance.

Rules:

- root motion belongs to the AttackDefinition movement profile;
- collision/world movement remains valid;
- client animation does not authorize a hit;
- distance is tuned per weapon/action;
- status/encumbrance/action eligibility can block the attack before it starts;
- Motion Warping may be used where a valid target alignment is needed.

---

# 8. Capsule / Target Spacing

Changing an enemy capsule radius can solve a local prototype spacing issue, but it is not the global combat-spacing architecture.

Combat spacing can consider:

- character capsule/body size;
- weapon reach;
- attack root-motion distance;
- target collision profile;
- AI preferred range;
- avoidance/navigation;
- Motion Warping targets.

Do not distort every enemy collision capsule merely to compensate for one attack animation.

---

# 9. Attack Speed Integration

AttackSpeed can modify montage play rate within attack-family bounds.

Combat locomotion remains independent from AttackSpeed unless the design explicitly links them.

A fast weapon can attack quickly while the character's actual run speed remains derived from normal movement state.

---

# 10. Multiplayer / Authority

Server owns combat action state and legal movement restrictions.

Clients can predict facing/root-motion presentation under normal Character Movement reconciliation, but cannot rotate/advance beyond allowed action state to create authoritative hits.

Remote characters reconstruct the same combat handling/action profile from compact replicated state.

---

# 11. Performance

- combat-specific animation layers activate only while relevant;
- distant NPCs use lower-cost profiles;
- no permanent Timeline just to keep facing the camera;
- facing correction runs only during the authored attack window;
- Motion Warping/IK/root-motion complexity is significance-scaled;
- weapon animation asset selection is event/context driven.

---

# 12. Acceptance Tests

1. Equipped two-handed weapon selects its combat locomotion profile.
2. Removing/stowing weapon returns to appropriate non-ready profile.
3. Encumbrance changes movement speed without combat animation overwriting it.
4. Attack facing adjusts only inside the configured window/angle.
5. Heavy attack cannot instantly rotate beyond its profile limit.
6. Root-motion step stops/reconciles against world collision.
7. Attack root movement cannot itself apply damage.
8. Different body profiles remain visually acceptable with combat poses.
9. Capsule/spacing changes are not required as a universal fix for every attack.
10. Player/NPC combat locomotion follows the same profile contract where practical.

## Core Rule

> Metaworld combat movement is layered on top of the canonical character-state resolver. Handling profiles select stance and locomotion presentation; attack definitions own bounded facing and root-motion commitment; collision and server action state still decide what movement and hits are actually valid.

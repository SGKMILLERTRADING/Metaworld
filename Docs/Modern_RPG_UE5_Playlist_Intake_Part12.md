# Episode 98 — Recipe Scroll / Crafting Recipe Loot Item

**Classification:** UPGRADE — APPROVED / RECIPE-KNOWLEDGE ITEM EXTENSION.

**Phase Ownership:** Crafting + Item DNA + Loot + Knowledge/Progression + UI.

Detailed companion:

`Docs/Recipe_Knowledge_Items_Learning_Unlock_System.md`

## Approved Tutorial Intent

- physical scroll/manual item can exist in world/inventory;
- item can teach a crafting recipe;
- recipe teaching items can be generated by Loot profiles;
- scroll receives world mesh/icon/description/presentation;
- crafting system recognizes learned recipe after use.

## Metaworld Upgrades

- physical scroll is a normal persistent ItemDefinition/ItemInstance with ownership, provenance, theft/evidence, weight/value and container state;
- it teaches stable `RecipeDefinitionID` values rather than a new enum containing every recipe name;
- do not derive recipe identity by display-name/string manipulation;
- teaching ItemDefinition may contain one or more `TeachesRecipeDefinitionIDs`;
- Loot system creates the actual scroll ItemInstance once and persists it; reopening a persistent chest cannot reroll unlimited recipes;
- scroll/manual consume policy is data-driven: single-use scroll, reusable book/manual, blueprint document, etc.;
- learning recipe is separate from legally/professionally being allowed to craft it;
- item-data struct expansion is not allowed to force every Widget to pass giant mutable ItemInfo copies; stable IDs/presentation snapshots remain preferred.

### Episode 98 Principle

> Recipe scrolls are real lootable knowledge items that point to stable RecipeDefinitionIDs; the physical object and the knowledge it can teach are separate persistent facts.

# Episode 99 — Learn Recipes / Known Recipe State / Tooltips

**Classification:** UPGRADE — APPROVED WITH STABLE-KNOWLEDGE CORRECTION.

**Phase Ownership:** Crafting Knowledge + Progression + UI + Notifications + Loot.

Detailed companions:

- `Docs/Recipe_Knowledge_Items_Learning_Unlock_System.md`
- `Docs/HUD_Notification_Feedback_System.md`
- `Docs/Notification_Deduplication_Cooldown_Priority_System.md`

## Approved Tutorial Intent

- player can learn recipe from a teaching item;
- already-known recipe is detected;
- duplicate knowledge is prevented;
- notifications explain `Learned Recipe` / `Already Known`;
- tooltip displays what recipe the item teaches and whether player already knows it;
- Crafting browser refreshes when knowledge changes;
- recipe teaching items can remain in loot tables.

## Metaworld Upgrades

- known recipes persist as stable RecipeDefinitionID knowledge records, not display strings;
- `RequestLearnRecipe(KnowledgeItemInstanceID)` is server-authoritative;
- item is consumed only after successful learning when its use policy says it is single-use;
- already-known result does not duplicate knowledge or repeatedly grant progression reward;
- selling/dropping a manual after learning it does not erase permanent learned knowledge;
- learning recipe does not bypass profession, skill, license, workstation, tool or material requirements;
- `OnRecipeKnowledgeChanged` refreshes relevant Crafting UI rather than polling/rebuilding continuously;
- tooltip derives Known/Unknown state from current character knowledge.

### Episode 99 Principle

> Learning a recipe adds one persistent RecipeDefinitionID to character knowledge. The UI reports that fact; it does not create or identify the knowledge through text formatting tricks.

# Episode 100 — Quickslot HUD / Assignment Menu Foundation

**Classification:** UPGRADE — APPROVED / NEW QUICK-ACCESS DOMAIN.

**Phase Ownership:** HUD + Inventory + Equipment + Controller/Input + UI.

Detailed companion:

`Docs/Quickslot_Hotbar_Item_Action_Assignment_System.md`

## Approved Tutorial Intent

- HUD can show multiple quick-access slots;
- each slot displays icon, input label and quantity;
- inventory context menu can offer `Set Quickslot`;
- modal/dim background can block accidental underlying interaction while choosing slot;
- slots can be built dynamically from configuration.

## Metaworld Upgrades

- quickslot is a shortcut/reference, not inventory and never duplicates/moves items;
- tutorial six-slot count is prototype data, not a universal limit;
- physical keyboard labels like `1,2,3,X,C,V` become Enhanced Input actions with device-aware glyphs;
- Xbox-style / PlayStation-style controller layouts may use D-pad, modifiers, radial selection or another validated profile;
- modal uses existing focus/input-layer architecture rather than a unique black-screen gameplay system;
- QuickslotID is independent of the physical button used to activate it;
- quickslot state is compact persistent assignment data, not Widget references.

### Episode 100 Principle

> A hotbar is configurable quick-access presentation over real inventory/equipment actions; assigning a slot never creates a second copy of the item.

# Episode 101 — Quickslot Assignment / HUD Persistence / UI Communication

**Classification:** UPGRADE — APPROVED WITH STABLE-REFERENCE CORRECTION.

**Phase Ownership:** Quickslots + Inventory + HUD + UI Data Contracts + Persistence.

Detailed companion:

`Docs/Quickslot_Hotbar_Item_Action_Assignment_System.md`

## Approved Tutorial Intent

- choose target quickslot from inventory item;
- slot updates item icon/count;
- HUD and inventory assignment UI stay synchronized;
- assignment survives closing/reopening menus;
- prevent multiple simultaneous assignment interactions;
- clean transient Widget references safely.

## Metaworld Upgrades

- do not save complete mutable ItemInfo structs in a Player Blueprint Map as persistent quickslot truth;
- store compact `S_MW_QuickslotAssignment` with stable IDs/assignment type;
- unique item can target exact ItemInstanceID;
- stackable consumable can target ItemDefinitionID/use profile so any current compatible stack can satisfy activation;
- quickslot manager broadcasts presentation changes to HUD; Widgets do not own assignment state;
- closing inventory/options UI does not require forced garbage collection; unbind/remove/deactivate references normally;
- one assignment edit state prevents conflicting clicks locally while authoritative item state remains unchanged.

### Episode 101 Principle

> Quickslot persistence stores stable references and intent, not copied item structs or transient Widget pointers.

# Episode 102 — Quickslot Activation / Item Resolution / Count Updates

**Classification:** UPGRADE — APPROVED WITH AUTHORITY CORRECTION.

**Phase Ownership:** Quickslots + Item Use + Equipment + Inventory + HUD + Input.

Detailed companion:

`Docs/Quickslot_Hotbar_Item_Action_Assignment_System.md`

## Approved Tutorial Intent

- pressing a quickslot action uses/equips the assigned item;
- stackable and non-stackable items resolve differently;
- quantity display updates after pickup/consumption;
- empty/unavailable slot gets clear overlay/state;
- activation events communicate to slot/HUD presentation.

## Metaworld Upgrades

- Enhanced Input `IA_MW_Quickslot_*` actions replace hardcoded Player Blueprint key events;
- slot activation resolves current authoritative availability before performing anything;
- potion shortcut can resolve an accessible compatible stack by ItemDefinition/use profile;
- unique weapon shortcut resolves exact ItemInstanceID;
- gameplay system/server performs RequestUseItem/RequestEquip/etc.; Widget/Event Dispatcher does not consume/equip authoritatively;
- counts update from Container deltas/aggregates rather than full-inventory scan or Widget child state;
- missing/sold/stolen/dropped/consumed item cannot be recreated by activating stale quickslot;
- unavailable slot can remain assigned but visually disabled according to profile.

### Episode 102 Principle

> Activating a quickslot requests the assigned gameplay intent against the current live item state; the hotbar can never manufacture a missing item simply because its icon is still visible.

# Episode 103 — Arrow Counts / Upgrades / Duplicate Quickslots / Final Polish

**Classification:** LOCKED + UPGRADE — QUICK-ACCESS INTEGRATION MAINTENANCE.

**Phase Ownership:** Quickslots + Ranged Ammo + Item Upgrades + Inventory + HUD + Controller.

Detailed companions:

- `Docs/Quickslot_Hotbar_Item_Action_Assignment_System.md`
- `Docs/Ranged_Weapons_Bow_Ammo_Quiver_Container_System.md`
- `Docs/Item_Upgrade_Reinforcement_Enhancement_System.md`

## Approved Tutorial Intent

- arrow shortcut displays total useful ammunition quantity;
- item upgrade must not break the quickslot;
- duplicate quickslot assignments are cleaned/managed;
- hover/focus visual polish improves readability;
- inventory/quickslot references remain correct after item-data changes.

## Metaworld Upgrades

- arrow quickslot should represent selected Ammo type/preference and aggregate compatible accessible count from quiver/approved ammo containers, not one stack's count;
- normal item upgrade preserves exact ItemInstanceID, so `Sword #84721 +2 -> +3` remains in the same quickslot automatically; only presentation/stat snapshot changes;
- no special `replace upgraded item in quickslot` workaround is needed for ordinary reinforcement;
- true transformation that creates a new ItemInstance may migrate assignment only under explicit transformation policy;
- duplicate assignment rule is configurable (`UniqueTargetOnly`, `AllowDuplicates`, etc.) rather than hardcoded globally;
- controller focus styling must match mouse hover information/state;
- ItemInfo struct changes do not require reconnecting quickslot logic everywhere because stable IDs/presentation contracts isolate the UI.

### Episode 103 Principle

> Quickslots survive ordinary ItemInstance state changes because they reference stable identity. Ammunition shortcuts resolve current accessible supply, and duplicate-slot behavior is a deliberate profile rule rather than a patch.
